# Scoped Edit 与自然语言修订

## 有界编辑合同 (`IMG-06`)

每次 edit 都声明精确 target/region、要改什么、必须保留什么、以及预期的
continuity impact。如果期望变更会改写 identity 或 accepted 上游事实，路由给
该 owner，不要伪装成局部 prompt revision。

## 1. 两类修改

- **对画面目标的 edit**：产出 `edit_delta` 提示词，例如改变一件衣服局部状态；不执行图像编辑。
- **对提示词本身的 revision**：创作者用自然语言修改规格；先提案 diff，接受后重渲染 Markdown。

二者都不能改写 assets 拥有的身份/variant 事实。若请求是“把这扇门移到另一面墙”但 Location 地理未变更，应发 assets/storyboard 相关 revision request，而不是悄悄写进 edit。

## 2. Edit-delta 配方

四个问题缺一不可：

```text
Target：哪个精确 artifact/hash、entity 和 region？
Change：哪些有边界、可观察的变化？
Preserve：身份、构图、光线、空间以及哪些未影响 entity/region 必须不变？
Continuity impact：预期对应哪个 accepted State/binding，有效到哪里？
```

### Target

- 用元信息绑定目标快照；copyable 正文用自然语言明确主体和区域。
- “改背景”“让她更狼狈”过宽；需要具体新 View/区域与可观察变化。
- 多个不相干 target 默认拆为多个 edit，防止 preserve 集失焦。

**场地反打/换角度的定点修改**：把一张已有 location plate 改成同一地点的另一个观察方向（反打、掉头看、换到对面），而不是从零重新生成一张新 plate 时，Target/Change 必须逐个重述每个主要固定锚点相对新机位的新位置，不能只写“换成反打镜头”“从另一侧看”这类方向性描述。

**为什么必须逐个重述**：编辑类操作是以现有画面的空间安排为强条件生成新画面的，模型倾向于尽量贴着输入图片已经确定的构图和位置作小幅调整，而不是主动去推理“如果镜头转到正对面，各个物体应该出现在镜面对称的哪个新位置”这种需要空间推理才能得出的结果。一句模糊的方向指令（“反打”“从另一侧看”）没有把这次真正需要发生的空间置换讲清楚，模型面对这种指令时常见的两种失败是：几乎没有真正改变布局（只是画面整体做了轻微调整，锚点还留在原来暗示的一侧），或者把各个锚点的位置搬得不一致、彼此矛盾（这扇门冲这边、那面墙又冲另一边），而不是执行一次真正连贯的镜面翻转。
唯一可靠的做法是把新方向下每个主要锚点的新位置明确写出来——“原视角中检修台在右侧、安全门在画面深处正中；换成对面视角后，检修台变为在画面左侧，安全门转到镜头身后（画面外），入口通道转为朝画面纵深方向延伸”——逐个交代，而不是留给模型自己推理镶嵌关系。

**好写法（逐个重述新位置）**：
> 本图为同一值班室的对面视角：原视角中检修台位于画面右侧、安全门在画面深处正中；换成这次的反向观察后，检修台改为在画面左侧，安全门转到镜头身后（画面外看不到），原本的入口通道转为朝画面纵深方向延伸。柜台、配电箱等其余固定锚点按同一镜面关系重新摆放。

**不好写法（只给方向，不给新位置）**：
> 把这张图换成反打镜头，其他保持不变。——模型没有被告知任何一个锚点具体该出现在新画面的哪里，容易只做表面调整或把各锚点的位置摆得互相矛盾。

### Change

按位置、方向、范围、程度、材质/色彩结果写 delta。例如“右袖肘部以下呈雨水浸湿后的深色，衣料贴合但无撕裂”，比“衣服弄湿”可控。不得补写未接受的伤势或剧情因果。

### Preserve

先列最容易被误改的高价值事实：面部/体态身份、未变 Look 部件、固定地理、道具轮廓与文字、构图/机位、光向、未选区域。不要写“其他全部保持”代替边界思考；允许最后用它概括已经点名的 preserve set。

**`craft_default`**：当创作者反馈“改多了”“跑掉了”时，正确反应是收紧 Change、扩充 Preserve，不是在同一版本上继续叠加新的改动去补救。

**为什么叠加编辑会累积伪影**：即使一次编辑的意图是“只改这一小块”，图片生成模型执行编辑时也不是逐像素的手术式操作——它是在原图和这次编辑指令共同条件下重新生成一次画面，任何没有被显式列进 Preserve 的区域，都是模型在统计上可以自由重新绘制的区域，哪怕改动很小：材质纹理被重新采样、光线被轻微重新分布、比例出现细微偏移、颗粒和色调也会带上这次重新生成特有的差异。单次编辑时，这种“未受保护区域的背景噪声”通常小到不会被注意，因为它相对于这次真正想要的改动来说很轻微。
但如果不回到编辑前的原图重新发一次更精确的指令，而是直接在上一次编辑的**输出**上继续叠加第二次编辑，第二次编辑自己的重新生成噪声会叠加在第一次已经产生的噪声之上，第三次又叠加在第二次之上——每一次叠加都是又一次让未受保护区域偏离原始画面的机会，而且这些微小偏移并不是彼此随机抵消的：它们往往顺着模型本身的固有倾向朝同一个方向累积（比如持续把皮肤磨得更光滑、色调持续偏暖、图案细节持续被简化），所以连续在同一血统上叠加编辑，即使每一步单看都“差不多”，也会measurably 累积成明显可见的漂移。
这也是为什么“改多了”之后正确的反应不是“我再在这张结果上小改一点试试看”——那只是往已经漂移的图片上再叠加第四次生成噪声。正确做法是把编辑前的**原图**重新当作基准，针对原图重新发出一次范围更窄的编辑指令（更小的 Change，更详尽的 Preserve），把编辑链收回成一步，而不是继续往下延伸。这和 Change/Preserve 的整体逻辑是一致的：Preserve 清单不只是文档，它是真正压住每次编辑的失控漂移的机制；任何一次没有收紧 Preserve 就被重新应用的编辑，都是在制造创作者正在抱怨的那种漂移的一部分。

**好写法（反馈“改多了”后收紧并回到原图重开一次）**：
> 第一次编辑要求“把右袖口改湿”，结果连带脸部光线也变了。正确修法：回到编辑前的原图，重新发一次编辑指令，Change 仍只是“右袖口以下呈现雨水浸湿的深色”，Preserve 里新增明确写出“脸部光线、五官、发际线与原图完全一致”，而不是在刚才那张已经跑偏的结果上再发一次“把脸调回来”的编辑。

**不好写法（在跑偏结果上继续叠加）**：
> 第一次编辑跑偏后，直接对这张跑偏的输出再发第二次编辑“脸部光线改回原来那样”，又对第二次结果发第三次编辑“袖口湿度还是不太对，再湿一点”。——每一次都在前一次已经带漂移的图上继续操作，三次叠加的漂移比任何一次单独编辑都更难收拢，且已经无法追溯到底哪次编辑造成了哪个具体变化。

每次 edit 只解决一个精确目标；确认这一步生效后，再决定是否需要下一次独立的 edit，而不是把多次尝试揉进一条不断松动的 preserve 集里。

### Continuity impact

引用 道具状态/Look/View 或提出 owner revision；记录受影响的 prompt/shot/keyframe，而非在 edit 中成为新的连续性权威。若没有影响，也明确 `none` 及理由。

- **`structural_invariant`**：target/hash/region、changes、preserve 和 impact 必须存在且没有显式冲突。
- **`reviewed_invariant`**：修改范围是否足够清楚、preserve 是否保护真正身份/地理，需要 reviewer 引用证据判断。
- **`craft_default`**：一次 edit 聚焦少量相互关联的 delta；复杂重构改用新 variant/plate。
- **`taste_option`**：变化的视觉强度由创作者决定，只要状态事实未变。

## 3. 自然语言 spec → diff → accept → rerender

用户不需要知道 JSONL 字段。对“把工作服换成深蓝，但保留脸和袖口油渍”执行：

1. **读取权威源**：当前 accepted spec、asset refs、recipe version 和 rendered hash。
2. **解释请求**：区分 prompt-owned 改动、source-owned 事实、含糊项与可能影响。
3. **生成候选 spec**：不覆盖 accepted spec；不确定值保持 unresolved。
4. **展示语义 diff**：字段路径、before、after、理由、影响、是否需上游 owner。
5. **展示新 prompt 预览**：让创作者看实际文案效果，而非只看字段。
6. **接受/拒绝**：接受才提交；拒绝使原 spec 与 Markdown byte-identical。
7. **重渲染**：accepted spec + recipe hash 唯一导出 Markdown，更新下游 stale 状态。

建议预览：

```markdown
### 提议修改 `IMG-...`
- `variant_delta.uniform.color`: `灰蓝` → `深蓝`
- `preserve`: 新增 `右袖口原有油渍的形状与位置`
- 未改：Character identity、服装剪裁、背景、构图、光向
- 影响：仅当前 Look prompt；若资产 Look 尚未接受深蓝色，先请求 assets 修改
- 未映射：无

**重渲染预览**
> ...
```

对“更有电影感”不能擅自选择一串风格字段。给两三个互斥但可解释的候选（如更明确光比/构图/色彩关系），标为 `taste_option` 让创作者选。

## 4. 缓存漂移的 restore/adopt

`image-prompts.md` 是缓存视图。发现它与 spec + recipe hash 不一致时暂停覆盖：

### Restore

- 展示当前手改文本与将恢复的 canonical preview；
- 创作者接受后从 accepted spec 重渲染；
- 不把手改内容静默写回 spec。

### Adopt

- 将可表示的手改语义解析为候选 spec diff；
- 逐条列出 `mapped`、`unmapped`、`lossy`；
- 有 unmapped/lossy 或改动 source-owned 事实时阻断 adopt，保留原文件与冲突副本；
- 安全且被接受后，先提交 spec，再重渲染成规范 Markdown。最终文本可能排版变化，但语义 diff 必须无损。

选择 `merge` 时也先生成候选 diff；不能以“最后写入者获胜”处理创作权威。

## 5. 失败与检查

### 失败征兆

- 直接改 accepted JSONL 或只改 Markdown；
- diff 只写“优化措辞”，没有字段和语义影响；
- 把身份、Location 地理、道具状态 在 prompt 层擅自改掉；
- edit 只有 Change 没有 Preserve；
- unmapped 手改被自动丢弃；拒绝后文件仍改变。

### 完成检查

- source-owned 请求已路由给正确 owner；
- 候选与 accepted 分离，diff 可读、可拒绝，预览可复制；
- accept 顺序是 spec commit 后 rerender；reject 不变；
- restore/adopt 都有预览，第三种 live hash 保留为冲突；
- 全流程不调用媒体生成或 provider API。
